# Missing role guard in mahasiswa violation page causes unhandled HTTP 500 for administrators

**ID:** vuln-0001
**Severity:** MEDIUM
**Found:** 2026-09-21 23:04:30 UTC
**Target:** http://172.17.112.1:8001
**Endpoint:** /pelanggaran
**Method:** GET
**CWE:** CWE-754
**CVSS:** 4.3
**Fix Effort:** Trivial

## Description

The student violation page (`/pelanggaran`) is rendered after only redirecting away sessions whose `user_type` is `dosen`. It performs no role check for any other non-student role, then dereferences student-only session fields (`angkatan`, `nim`). An authenticated administrator reaching this route triggers a PHP undefined-array-key warning that the framework's error handler converts to an uncaught exception, returning **HTTP 500 Internal Server Error** instead of a controlled `403 Forbidden`.

## Evidence

Administrator session against the student violation page:

```http
GET /pelanggaran HTTP/1.1
Host: 172.17.112.1:8001
Cookie: PHPSESSID=<admin session>

HTTP/1.1 500 Internal Server Error
Content-Type: text/html; charset=UTF-8

<title>500 - Sistem Bermasalah | DiscipLink</title>
```

Contrast — same administrator session, lecturer page denies in a controlled manner:

```http
GET /pelanggaran/dosen HTTP/1.1
Host: 172.17.112.1:8001
Cookie: PHPSESSID=<admin session>

HTTP/1.1 403 Forbidden
```

Control — a `mahasiswa` session reaches the same page normally:

```http
GET /pelanggaran HTTP/1.1
Host: 172.17.112.1:8001
Cookie: PHPSESSID=<mahasiswa session>

HTTP/1.1 200 OK
```

## Impact

An authenticated administrator (or any authenticated session that is neither `mahasiswa` nor `dosen`) can force an unhandled server-side exception on a route they are not authorised to view. This is an availability and access-control-consistency defect: the page fails with a generic error rather than a deliberate denial, and the same class of bug was already remediated elsewhere (`/pelanggaran/dosen` returns `403` for administrators). The generic error page does not leak stack traces or internal paths, so confidentiality impact is limited; there is no state change or data exposure.

## Technical Analysis

`views/pelanggaran/pelanggaran-page.php` opens with a login check and a single role redirect:

```php title=views/pelanggaran/pelanggaran-page.php startLineNumber=7 endLineNumber=14
if (!isset($_SESSION['username'])) {
    app_redirect_page('page.login');
}


if ($_SESSION['user_type'] === 'dosen') {
    app_redirect_page('page.pelanggaran_dosen');
}
```

Only `dosen` is diverted. Control then falls through to student-only data access:

```php title=views/pelanggaran/pelanggaran-page.php startLineNumber=17 endLineNumber=30
$userData = $_SESSION['user_data'];

$currentYear = date('Y');
$currentMonth = date('n');
$yearDiff = $currentYear - $userData['angkatan'];
$semester = ($yearDiff * 2);
if ($currentMonth >= 8) { // Semester ganjil dimulai sekitar Agustus
    $semester += 1;
}

// tabel
$pelanggaranController = new PelanggaranController();
$nim = $userData['nim'];
```

`$_SESSION['user_data']` is the raw authentication row returned by `UserController::login()`. For an administrator it is the `ADMIN` row (`id_admin`, `NIP`, `nama_admin`, `password`) and contains neither `angkatan` nor `nim`. Accessing `$userData['angkatan']` on line 21 emits an undefined-array-key warning; `router.php` installs a `set_error_handler` that promotes warnings to `ErrorException`, and the registered exception handler renders the 500 error page. The response is a generic `500 - Sistem Bermasalah` page with no stack trace (display_errors is disabled).

The sibling lecturer page applies a fail-closed role guard and returns `403` for administrators, so the intended behaviour for an out-of-role request is a controlled denial. The student page is missing the equivalent guard.

## Proof of Concept

1. Authenticate as an administrator (`ADMIN002` / `admin456`) and retain the session cookie.
2. Request the student violation page: `GET /pelanggaran`.
3. Observe that the server responds with `HTTP/1.1 500 Internal Server Error` and renders the generic "500 - Sistem Bermasalah" error page.
4. For contrast, request the lecturer page `GET /pelanggaran/dosen` with the same administrator session and observe a controlled `HTTP/1.1 403 Forbidden`.

```python
import re
import requests

BASE = "http://172.17.112.1:8001"

s = requests.Session()
# 1. fetch login page + CSRF token
login_page = s.get(f"{BASE}/login").text
csrf = re.search(r'name="csrf_token" value="([^"]+)"', login_page).group(1)

# 2. authenticate as administrator
s.post(f"{BASE}/action/login", data={
    "csrf_token": csrf,
    "username": "ADMIN002",
    "password": "admin456",
    "user_type": "admin",
})

# 3. administrator requests the student-only violation page
r = s.get(f"{BASE}/pelanggaran")
print("GET /pelanggaran        ->", r.status_code)   # 500 (unhandled exception)

# 4. contrast: the guarded lecturer page denies correctly
r2 = s.get(f"{BASE}/pelanggaran/dosen")
print("GET /pelanggaran/dosen  ->", r2.status_code)  # 403 (fail-closed)
```

## Code Analysis

**Location 1:** `views/pelanggaran/pelanggaran-page.php` (lines 12-14)
  Enforce student-only access with a fail-closed role guard
  ```
  if ($_SESSION['user_type'] === 'dosen') {
      app_redirect_page('page.pelanggaran_dosen');
  }
  ```

  **Suggested Fix:**
```diff
- if ($_SESSION['user_type'] === 'dosen') {
-     app_redirect_page('page.pelanggaran_dosen');
- }
+ if ($_SESSION['user_type'] === 'dosen') {
+     app_redirect_page('page.pelanggaran_dosen');
+ }
+ 
+ if (($_SESSION['user_type'] ?? '') !== 'mahasiswa') {
+     app_abort_forbidden();
+ }
```

## Remediation

Apply a fail-closed role guard to the student violation page. Immediately after the existing `dosen` redirect in `views/pelanggaran/pelanggaran-page.php`, abort with a controlled `403` when the session role is not `mahasiswa`, reusing the existing `app_abort_forbidden()` helper rather than falling through to student-only field access. More broadly, replace the ad-hoc per-view role checks with a single shared guard (e.g. `app_require_role('mahasiswa')`) invoked at the top of every role-scoped view and action handler, so that a request from an unexpected role always yields a deliberate denial instead of an unhandled exception.

## Assumptions

Requires an authenticated session whose `user_type` is neither `mahasiswa` nor `dosen` (e.g. `admin`). The impact is bounded to a controlled-denial failure (500 instead of 403) on one route; no data is exposed and no state is modified.
