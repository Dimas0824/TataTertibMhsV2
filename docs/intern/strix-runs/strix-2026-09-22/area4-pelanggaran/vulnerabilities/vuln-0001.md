# Missing workflow-state check allows deletion of finalized violation records

**ID:** vuln-0001
**Severity:** HIGH
**Found:** 2026-09-21 23:14:30 UTC
**Target:** http://172.17.112.1:8001
**Endpoint:** /action/pelanggaran
**Method:** POST
**CWE:** CWE-863
**CVSS:** 7.1
**Fix Effort:** Low

## Description

The violation-report deletion endpoint (`POST /action/pelanggaran?action=delete`) enforces reporter ownership but omits any workflow-state check. As a result, a lecturer can permanently delete a violation record whose status is `selesai` (finalized), even though the user interface disables the delete control for finalized records and the edit path explicitly rejects modifications once a record is finalized. This permits destruction of adjudicated disciplinary history and its associated sanction record.

## Evidence

Reproduced twice consecutively against the running instance. The record is confirmed as `selesai` (the UI row renders the "Selesai" button and the delete control is `disabled`), the server refuses to edit it, yet the delete request succeeds and the row count drops.

```
1) POST /action/pelanggaran?action=confirm_selesai  id_detail=<token>
   -> 302  flash: {"type":"success","message":"Laporan berhasil dikonfirmasi selesai."}
   -> row state: "Selesai" ; delete button rendered `disabled`

2) POST /action/pelanggaran   update=1  id_detail=<same token>
   -> flash: {"type":"error","message":"Data tidak dapat diedit karena tugas atau laporan sudah selesai."}

3) POST /action/pelanggaran?action=delete  id_detail=<same token>
   -> 302  Location: /pelanggaran/dosen
   -> next GET flash: {"type":"success","message":"Laporan berhasil dihapus."}
   -> row count 52 -> 51
```

Raw delete request/response:

```
POST /action/pelanggaran?action=delete HTTP/1.1
Host: 172.17.112.1:8001
Cookie: PHPSESSID=<dosen session>
Content-Type: application/x-www-form-urlencoded

csrf_token=<session csrf>&id_detail=<s1. token bound to this session>

HTTP/1.1 302 Found
Location: /pelanggaran/dosen
```

```
trial 0: delete-selesai msg=Laporan berhasil dihapus. rows 52->51
trial 1: delete-selesai msg=Laporan berhasil dihapus. rows 52->51
```

## Impact

An authenticated lecturer can permanently erase a finalized (adjudicated) disciplinary violation and its sanction history for a student, together with the associated notifications. Finalized records are intended to be immutable (the edit path refuses them and the UI disables the delete control), so the deletion silently defeats the append-only intent of the case workflow, removes the audit/disciplinary record for the student, and can be used to conceal a completed sanction. The data loss is irrecoverable from within the application.

## Technical Analysis

The delete handler resolves the client-supplied obfuscated identifier and delegates to the model:

`request/handler-pelanggaran.php` (delete branch) only verifies the session role is `dosen` and resolves `id_detail`, then calls `hapusDetailPelanggaran($nidn, $idDetail)`.

`models/Pelanggaran.php::hapusDetailPelanggaranByDosen()` verifies **ownership only** (the reporter), then deletes notifications and the detail row:

```php title=models/Pelanggaran.php
"SELECT dp.id_detail
 FROM DETAIL_PELANGGARAN dp
 JOIN DOSEN d ON dp.id_dosen = d.id_dosen
 WHERE dp.id_detail = ?
   AND d.nidn = ?
 LIMIT 1"
...
"DELETE FROM DETAIL_PELANGGARAN WHERE id_detail = ?"
```

No `status`/`status_tugas` predicate is applied. By contrast, the sibling operations enforce the finalized-state guard:

- `models/Pelanggaran.php::updateDetailPelanggaran()` — `if ($isLaporanSelesai || $isTugasSelesai) { throw new RuntimeException('Edit tidak diizinkan karena tugas atau laporan sudah selesai.'); }`
- `views/pelanggaran/pelanggaran-dosen.php` — `$canDelete = $isDosenPelapor && !$isSelesai;` with `disabled` on the button, and the edit view refuses to render/allow the edit.

Because the server-side delete path lacks the guard that the edit path (and the UI) applies, an authenticated reporter can remove a record the system otherwise treats as frozen. The authorization boundary (reporter-only) is intact — the defect is the inconsistent enforcement of workflow state (CWE-863).

## Proof of Concept

1. Authenticate as the reporting lecturer (`1234567890` / `password123`).
2. Create a level-V violation for student NIM `2341238902` (POST `/action/pelanggaran` with `store=1`, a valid `jenisPelanggaran` token, and `nim`).
3. Authenticate as the student (`2341238902` / `password456`) and upload the required statement letter (POST `/action/upload` with `suratPernyataan`), making the record confirmable.
4. As the lecturer, confirm the record (POST `/action/pelanggaran?action=confirm_selesai` with the record's `id_detail` token). Response: **"Laporan berhasil dikonfirmasi selesai."** The record now renders as **Selesai** with its delete control disabled.
5. Attempt to edit the same record (POST `/action/pelanggaran` with `update=1`). Response: **"Data tidak dapat diedit karena tugas atau laporan sudah selesai."** — confirming the server treats the record as frozen.
6. Delete the same record (POST `/action/pelanggaran?action=delete` with the same `id_detail` token). Response: **"Laporan berhasil dihapus."** The record count decreases (52 → 51), proving the finalized record was permanently removed.

## Remediation

Apply the same finalized-state guard used by the edit path to the delete path. In the model deletion routine, first load the record's `status` and `status_tugas` and refuse deletion when the record is finalized (status in `selesai`/`done`, or status_tugas finalized), returning an error to the caller. Mirror this check in the request handler's delete branch so the state is enforced before any delete statement executes. For finalized records, prefer a soft-delete or explicit "void/annul" state that preserves the original record and its audit history rather than destroying the row and its notifications. Add tests asserting that delete is rejected for finalized records and accepted only for active ones.

## Assumptions

Assumes an authenticated lecturer account that is the reporter of the target record. The authorization boundary (reporter-only deletion) is enforced and was verified; the defect is the missing workflow-state check, which affects only records the caller already owns. Requires a record to reach the `selesai` state, which is a normal workflow outcome.
