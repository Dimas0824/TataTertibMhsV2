# PHP session.use_strict_mode disabled — server adopts arbitrary client-supplied session identifiers

**ID:** vuln-0001
**Severity:** MEDIUM
**Found:** 2026-09-21 22:57:14 UTC
**Target:** http://172.17.112.1:8001
**CWE:** CWE-384
**CVSS:** 4.2
**Fix Effort:** Trivial

## Description

The application runs with PHP's `session.use_strict_mode` disabled (the PHP default). As a result, the server accepts any client-supplied `PHPSESSID` value, materializes a server-side session under that exact identifier, and persists state in it. Because the session ID is attacker-chosen, an attacker who can influence a victim's cookie value (e.g. via a sibling-domain XSS or a network man-in-the-middle on the plaintext-HTTP deployment, where the session cookie carries no `Secure` flag) can pre-create a session whose identifier and CSRF token are fully known to the attacker before the victim ever authenticates.

## Evidence

Request 1 — arbitrary, never-seen session identifier supplied by the client:

```
GET /login HTTP/1.1
Host: 172.17.112.1:8001
Cookie: PHPSESSID=auditreportauditreport0001
```

Response 1 — note the absence of any `Set-Cookie` header, i.e. the server accepted the supplied identifier verbatim:

```
HTTP/1.1 200 OK
Date: Mon, 21 Sep 2026 22:56:29 GMT
Content-type: text/html; charset=UTF-8
(no Set-Cookie header)
```

Requests 2/3 — same client-chosen identifier resolves to the same server-side session (identical CSRF token persisted across requests):

```
token#1=dabefbdb4dbfdd271225a18805650f120465c29e09d8475108b9a768c988b623
token#2=dabefbdb4dbfdd271225a18805650f120465c29e09d8475108b9a768c988b623
identical=YES
```

Containment check — replaying the planted identifier after authenticating in that session is unauthenticated (login rotates the identifier):

```
GET /admin with Cookie: PHPSESSID=<planted>  ->  HTTP 302 (Location: /login)
```

## Impact

This is a session-fixation enabler (CWE-384). In the tested configuration the impact is limited because the login path calls `session_regenerate_id(true)` and clears the CSRF token, so a pre-planted identifier is replaced on authentication and cannot be replayed as an authenticated session. The residual risk is that the server will honour any externally supplied session identifier and will create/persist session state (including the CSRF token) under it, which broadens the session-fixation attack surface and enables unbounded low-cost server-side session materialization. This is a defence-in-depth weakness, not a directly exploitable authentication bypass in the current build.

## Technical Analysis

PHP's `session.use_strict_mode` directive governs whether an unknown session ID supplied by the client is rejected or adopted. When it is `0` (disabled — the PHP default), `session_start()` accepts the client-provided identifier verbatim and initialises the session store under it.

The application hardens the session cookie (`session_set_cookie_params` with `HttpOnly`/`SameSite=Lax`/conditional `Secure`, see `helpers/token_helper.php`) and rotates the identifier on privilege change (`session_regenerate_id(true)` in `controllers/UserController.php` login path, and in `request/handler-login.php`), but it never enables `session.use_strict_mode`. Consequently:

1. A request carrying an arbitrary, previously non-existent `PHPSESSID` is accepted without a replacement `Set-Cookie`.
2. Repeated requests with the same attacker-chosen identifier resolve to the **same** server-side session — verified by an identical `csrf_token` returned across requests (`helpers/token_helper.php::app_csrf_token()` persists the token in `$_SESSION`).

The mitigation is a one-line `php.ini` / runtime directive change to `session.use_strict_mode = 1`, which makes PHP reject unknown client-supplied IDs and generate a fresh one.

## Proof of Concept

1. Send a request to `/login` with a `Cookie: PHPSESSID=<attacker-chosen 26-char value>` that has never been seen by the server.
2. Observe the response: it does **not** include a replacement `Set-Cookie` header, proving the server adopted the supplied identifier.
3. Repeat the same request with the same arbitrary identifier twice and extract the `csrf_token` hidden field from each response.
4. Observe both responses return an identical `csrf_token`, proving a persistent server-side session exists under the attacker-chosen identifier.
5. Attempt the fixation end-to-end: authenticate in the planted session, then replay the originally planted identifier — the replay is unauthenticated (HTTP 302 to `/login`), confirming the login-time rotation contains the impact.

````bash
# 1) Server adopts an arbitrary, never-seen session id (no Set-Cookie in response)
curl -s -D - -o /dev/null \
  -H 'Cookie: PHPSESSID=auditreportauditreport0001' \
  http://172.17.112.1:8001/login
# -> HTTP/1.1 200 OK, and NO Set-Cookie header is returned.

# 2) Same arbitrary id resolves to the same server-side session state
T1=$(curl -s -H 'Cookie: PHPSESSID=auditreportauditreport0001' \
        http://172.17.112.1:8001/login | grep -oP 'name="csrf_token" value="\K[^"]+')
T2=$(curl -s -H 'Cookie: PHPSESSID=auditreportauditreport0001' \
        http://172.17.112.1:8001/login | grep -oP 'name="csrf_token" value="\K[^"]+')
echo "token#1=$T1"
echo "token#2=$T2"   # identical => state persisted under the attacker-chosen id
```

```python
import re, requests

BASE = "http://172.17.112.1:8001"
SID  = "auditreportauditreport0001"      # attacker-chosen, never issued by the server

r = requests.get(f"{BASE}/login", cookies={"PHPSESSID": SID})
print("Set-Cookie present:", "set-cookie" in {k.lower() for k in r.headers})  # False
t1 = re.search(r'name="csrf_token" value="([^"]+)"', r.text).group(1)

r2 = requests.get(f"{BASE}/login", cookies={"PHPSESSID": SID})
t2 = re.search(r'name="csrf_token" value="([^"]+)"', r2.text).group(1)
print("server-side session persisted under attacker id:", t1 == t2)  # True
````

## Remediation

Enable strict session mode so PHP rejects unrecognised client-supplied session identifiers and issues a fresh one instead. Set `session.use_strict_mode = 1` in the effective `php.ini` (or via `ini_set('session.use_strict_mode', '1')` before `session_start()` in the bootstrap), and add a regression assertion to the session lifecycle test suite that a randomised, previously-unseen `PHPSESSID` is replaced by a server-generated value. This complements the existing login-time identifier rotation and closes the remaining session-fixation gap.

## Assumptions

Exploitation as a full authentication-fixation attack requires the attacker to first be able to set or predict the victim's `PHPSESSID` cookie — attainable through a sibling-subdomain cookie-injection/XSS or a network man-in-the-middle given the plaintext-HTTP deployment and the session cookie lacking the `Secure` flag. Even then, the application's login-time `session_regenerate_id(true)` and CSRF-token reset neutralise the attack, so the confirmed impact is a hardening/defence-in-depth weakness rather than a working account takeover in the current build. Verified on a locally hosted, self-owned instance.
