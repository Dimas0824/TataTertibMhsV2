# NUL-byte truncation in password verification allows authentication with a NUL-suffixed password

**ID:** vuln-0001
**Severity:** HIGH
**Found:** 2026-09-21 14:32:59 UTC
**Target:** http://172.17.112.1:8001
**Endpoint:** /action/login
**Method:** POST
**CWE:** CWE-230
**CVSS:** 7.4
**Fix Effort:** Low

## Description

The login password comparison is not length-exact: any password value containing a NUL byte (`%00`) is compared only up to that byte. As a result, submitting a **valid password followed by `%00` and arbitrary trailing data** authenticates successfully, while the same value without the NUL byte is rejected. This is a weakness in the authentication integrity check (CWE-230 Improper Handling of NUL Bytes / CWE-20).

## Evidence

Request (NUL byte in password, percent-encoded as `%00`):

```http
POST /action/login HTTP/1.1
Host: 172.17.112.1:8001
Cookie: PHPSESSID=<session>
Content-Type: application/x-www-form-urlencoded
Content-Length: 96

csrf_token=<valid-token>&user_type=nim&username=2341238901&password=password123%00INJECTED
```

Response (authentication succeeds):

```http
HTTP/1.1 302 Found
Set-Cookie: PHPSESSID=49k173fdfomf8hv36du81lka5o; path=/; HttpOnly; SameSite=Lax
Location: /pelanggaran

```

Control request (same password, no NUL byte):

```http
POST /action/login HTTP/1.1
Host: 172.17.112.1:8001
Cookie: PHPSESSID=<session>
Content-Type: application/x-www-form-urlencoded

csrf_token=<valid-token>&user_type=nim&username=2341238901&password=password123XINJECTED
```

Response (authentication fails):

```http
HTTP/1.1 302 Found
Location: /login

```

Additional differential probes confirming the NUL truncation (all in scope, same endpoint):

```
password12%00junk     -> Location: /login        (prefix shorter than real password: rejected)
password124%00XYZ     -> Location: /login        (wrong base password: rejected)
password123%00XYZ     -> Location: /pelanggaran  (correct password + NUL + suffix: accepted)
%00password123        -> Location: /login        (leading NUL: rejected)
```

The same behavior was reproduced for the `dosen` account (`nidn` `1234567890`, real password `password123`): `password123%00junk` → `Location: /pelanggaran/dosen`; `password12%00junk` → `Location: /login`.

## Impact

An attacker who learns or guesses a valid password prefix — or who has any means of capturing an individually-valid credential — can submit it with an appended `%00<arbitrary payload>` and still be authenticated. The client-supplied password is silently truncated by the underlying bcrypt verifier, so the effective credential space is shortened and any trailing data is discarded. This undermines the integrity of the credential check, defeats any input-normalization or length validation applied to the password, and means a password that is a correct prefix of the real password followed by a NUL byte is honored. It does not allow login without knowledge of at least the correct prefix, so on its own it is an authentication-integrity defect rather than a full unauthenticated bypass; however, it materially weakens the username/password control and should be fixed prior to any external deployment.

## Technical Analysis

The login handler reads the password as a raw string and passes it to the model without rejecting NUL bytes:

```php title=request/handler-login.php startLineNumber=24 endLineNumber=26
$userType = $_POST['user_type'] ?? null;
$username = trim((string) ($_POST['username'] ?? ''));
$password = (string) ($_POST['password'] ?? '');
```

The credential check is a standard bcrypt verification:

```php title=models/User.php startLineNumber=56 endLineNumber=60
$storedPassword = (string) $user['password'];

// Hashed credentials only; legacy plaintext rows are rejected here and must be
// migrated once via: php database/cli/hash-plaintext-passwords.php
$isValid = str_starts_with($storedPassword, '$2') && password_verify($plainPassword, $storedPassword);
```

PHP's bcrypt verifier (`password_verify` over the `$2y$` scheme) uses C-string semantics for the candidate password and stops at the first NUL byte. Consequently the string `password123\0XYZ` is compared as `password123`, and verification succeeds. The username field is unaffected because it is normalized with `trim()` (which does not strip NUL) and then compared as a whole against the database column, so `2341238901\0junk` legitimately fails. The asymmetry — password truncates at NUL, username does not — isolates the defect to the password verification path.

Verified behaviors against the live target (`nim` account `2341238901`, real password `password123`), all via `POST /action/login` with a valid CSRF token:

| Submitted `password` value | Result |
| --- | --- |
| `password123%00INJECTED` | `302 Found` → `Location: /pelanggaran` (authenticated) |
| `password123XINJECTED` | `302 Found` → `Location: /login` (rejected) |
| `password12%00junk` | `302 Found` → `Location: /login` (rejected) |
| `password124%00XYZ` | `302 Found` → `Location: /login` (rejected) |
| `%00password123` | `302 Found` → `Location: /login` (rejected) |

The pattern (± arbitrary suffix only when a NUL immediately follows the correctly-typed password) is exactly consistent with NUL-terminated comparison in the password verifier.

## Proof of Concept

1. Request the login page and extract the `csrf_token` value together with the session cookie.
2. Submit `POST /action/login` with `Content-Type: application/x-www-form-urlencoded` and the body `csrf_token=<token>&user_type=nim&username=2341238901&password=password123%00INJECTED` (the `%00` is the URL-encoded NUL byte; percent-encoding is used so the byte is decoded by the PHP form parser).
3. Observe a `302` response with `Location: /pelanggaran` and a **new** `Set-Cookie: PHPSESSID=...` — the login succeeded.
4. As a control, repeat with `password=password123XINJECTED` (no NUL). The response is `302` with `Location: /login`, confirming the difference is caused solely by the NUL byte.

```bash
T=http://172.17.112.1:8001
JAR=/tmp/nul.jar
rm -f "$JAR"

# 1. Fetch login page + CSRF token
curl -s -c "$JAR" "$T/login" -o /tmp/login.html
TOKEN=$(grep -oP 'name="csrf_token" value="\K[^"]+' /tmp/login.html | head -1)

# 2. Valid password + %00 + arbitrary suffix  -> AUTHENTICATED
curl -s -i -b "$JAR" -X POST "$T/action/login" \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  --data-raw "csrf_token=$TOKEN&user_type=nim&username=2341238901&password=password123%00INJECTED" \
  | grep -iE '^HTTP|^Location|^Set-Cookie'

# 3. Control: same value WITHOUT the NUL byte -> REJECTED
curl -s -i -b "$JAR" -X POST "$T/action/login" \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  --data-raw "csrf_token=$TOKEN&user_type=nim&username=2341238901&password=password123XINJECTED" \
  | grep -iE '^HTTP|^Location'
```

## Code Analysis

**Location 1:** `request/handler-login.php` (lines 24-34)

  ```

          $username = trim((string) ($_POST['username'] ?? ''));
          $password = (string) ($_POST['password'] ?? '');
  
          if ($username === '' || $password === '') {
              set_app_flash_modal('error', 'Username dan password wajib diisi.');
              app_redirect('views/auth/login.php');
          }
  ```

```diff

-         $password = (string) ($_POST['password'] ?? '');
-
```

## Remediation

Reject credentials containing NUL bytes before they reach the password verifier, and ensure the comparison is performed on the exact, bounded byte sequence. Concretely: after reading `$_POST['password']`, if `strpos($password, "\0") !== false` then reject the login attempt and record an audit event; additionally enforce a maximum password length (e.g. 72 bytes for bcrypt) so inputs cannot be silently truncated. Prefer a verification routine whose semantics are explicitly length-delimited rather than relying on the verifier's C-string behavior. Apply the same NUL rejection to the username to keep input handling uniform. Add a regression test asserting that a valid password suffixed with `\0` plus data fails authentication.

## Assumptions

Requires the attacker to already know (or guess) the correct password up to the point of the injected NUL byte. The finding demonstrates that the password verification is not length-exact and that trailing data after a NUL byte is silently discarded; it is not a credential-free bypass. bcrypt's handling of the NUL byte depends on the PHP/OpenSSL build; behavior was confirmed on the deployed instance.
