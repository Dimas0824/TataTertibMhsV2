# No absolute session lifetime and no invalidation of concurrent sessions

**ID:** vuln-0002
**Severity:** LOW
**Found:** 2026-09-21 14:40:50 UTC
**Target:** http://172.17.112.1:8001
**Endpoint:** /action/login, /action/logout
**Method:** POST
**CWE:** CWE-613
**CVSS:** 3.7
**Fix Effort:** Medium

## Description

The application enforces only a 30-minute **idle** timeout that is reset on every request; there is no absolute session lifetime. In addition, an account may hold an unlimited number of simultaneous sessions, and a new login does not invalidate existing sessions. A captured session cookie therefore remains usable indefinitely as long as it is used periodically, and logging in again does not revoke a hijacked session.

Two live sessions for the same `mahasiswa` account:

The idle timer is refreshed on every request, so continuous activity keeps the session alive with no upper bound.

```php title=helpers/token_helper.php startLineNumber=107 endLineNumber=119
$lastActivity = isset($_SESSION['__last_activity']) ? (int) $_SESSION['__last_activity'] : 0;
if ($lastActivity > 0 && ($now - $lastActivity) > $idleTtl) {
    // ...expire...
}
$_SESSION['__last_activity'] = $now; // refreshed on every request
```

## Impact

A stolen session cookie is valid for the entire browsing lifetime of the victim rather than being bounded by an absolute cap, and re-authentication does not evict the attacker. Combined with the missing `Secure` attribute, a captured `PHPSESSID` provides durable, unaudited access as the victim (including `admin`), extending the window for data theft and fraudulent state changes.

## Technical Analysis

Session liveness is governed entirely by `app_session_touch_or_expire()` in `helpers/token_helper.php`, invoked once per request from `router.php`. It records only a last-activity timestamp and expires the session purely on idle time:

```php title=helpers/token_helper.php startLineNumber=105 endLineNumber=120
$now = time();
$lastActivity = isset($_SESSION['__last_activity']) ? (int) $_SESSION['__last_activity'] : 0;

if ($lastActivity > 0 && ($now - $lastActivity) > $idleTtl) {
    $_SESSION = [];
    if (session_status() === PHP_SESSION_ACTIVE) {
        session_destroy();
    }
    @session_start();
    $_SESSION['__last_activity'] = $now;
    return false;
}

$_SESSION['__last_activity'] = $now;
return true;
```

No creation/issued timestamp is stored, so there is no absolute lifetime. Because `__last_activity` is updated on every request, any periodic request resets the window indefinitely.

On authentication, `controllers/UserController.php` (lines 56-62) regenerates the session identifier but does not enumerate or invalidate the account's other sessions; nothing in the schema or handlers caps the number of live sessions per user. The verified behaviour is that two logins for one account yield two simultaneously valid sessions.

## Proof of Concept

1. Authenticate the same account twice from two independent cookie jars.
2. Confirm both session identifiers remain simultaneously valid against a protected page (`/pelanggaran` or `/pelanggaran/dosen`) returning HTTP 200.
3. Continue issuing requests on the older session; observe it is never invalidated by the newer login.
4. (Lifetime) Programmatically, only `__last_activity` is checked; there is no creation timestamp or absolute cap, so periodic requests keep the session alive without limit.

```bash
login() { # user pass type jar
  jar=$4; rm -f $jar
  tok=$(curl -s -c $jar http://172.17.112.1:8001/login \
        | grep -o 'name="csrf_token" value="[0-9a-f]*"' | grep -o '[0-9a-f]\{64\}' | head -1)
  curl -s -o /dev/null -b $jar -c $jar -X POST http://172.17.112.1:8001/action/login \
       --data-urlencode "csrf_token=$tok" --data-urlencode "user_type=$3" \
       --data-urlencode "username=$1" --data-urlencode "password=$2"
}

login 1234567890 password123 dosen cA.txt
login 1234567890 password123 dosen cB.txt   # second session, same account

curl -s -o /dev/null -w "A /pelanggaran/dosen -> %{http_code}\n" -b cA.txt http://172.17.112.1:8001/pelanggaran/dosen
curl -s -o /dev/null -w "B /pelanggaran/dosen -> %{http_code}\n" -b cB.txt http://172.17.112.1:8001/pelanggaran/dosen
# both return 200 => concurrent sessions coexist, neither revoked
```

## Remediation

Store a session creation timestamp (e.g., `__created_at`) at login and reject the session after an absolute lifetime (for example 8-12 hours) regardless of activity, forcing re-authentication. Track the server-side session inventory per user and, on each successful login (and on password change), invalidate all other sessions for that account. Optionally cap concurrent sessions and require re-authentication for logout. Enable server-side session garbage collection with a matching `gc_maxlifetime`.

## Assumptions

Assumes an attacker who has captured a session cookie (e.g., via the missing-Secure issue, a shared/untrusted device, or network interception). The findings are configuration/lifecycle weaknesses that do not by themselves grant access without a stolen session or a compromised browser. The concurrency observation applies to any authenticated account, including `admin`.
