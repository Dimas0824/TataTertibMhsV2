# Session cookie issued without Secure flag on HTTPS-terminated (proxy) requests

**ID:** vuln-0001
**Severity:** MEDIUM
**Found:** 2026-09-21 14:40:38 UTC
**Target:** http://172.17.112.1:8001
**Endpoint:** /login (Set-Cookie for PHPSESSID)
**Method:** GET
**CWE:** CWE-614
**CVSS:** 5.9
**Fix Effort:** Low

## Description

The `PHPSESSID` session cookie is only marked `Secure` when the PHP variable `$_SERVER['HTTPS']` is literally set. When TLS is terminated by a reverse proxy that signals HTTPS through `X-Forwarded-Proto` (or `SERVER_PORT=443`) instead of setting `HTTPS`, the application still treats the connection as HTTPS for other features (HSTS is emitted) but issues the session cookie **without** the `Secure` attribute. The cookie can therefore be transmitted over cleartext HTTP, exposing the session to interception.

## Evidence

Request (application treats as HTTPS):

```http
GET /login HTTP/1.1
Host: dimspersonal.my.id
X-Forwarded-Proto: https
```

Response (note HSTS present, cookie lacks `Secure`):

```http
HTTP/1.1 200 OK
Set-Cookie: PHPSESSID=hh5q0hgt2qii0p2q2dd06juaqh; path=/; HttpOnly; SameSite=Lax
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
```

Baseline plain HTTP:

```http
Set-Cookie: PHPSESSID=1pbhqcjlkd5f40aj7uatn49ma8; path=/; HttpOnly; SameSite=Lax
```

## Impact

If the deployment sits behind a TLS-terminating proxy (the documented canonical deployment is `https://dimspersonal.my.id`), the session cookie is not restricted to HTTPS. An attacker positioned to observe or force a single cleartext HTTP request (e.g., a downgrade link, an `http://` subresource/redirect, or a network adversary) can capture a valid `PHPSESSID` and hijack the authenticated session of any role, including `admin`. This undermines the confidentiality of all authenticated functionality (violation records, reports, user actions, admin news/tatib CRUD).

## Technical Analysis

Session cookie parameters are configured in a single place:

```php title=helpers/token_helper.php startLineNumber=13 endLineNumber=17
session_set_cookie_params([
    'secure' => (!empty($_SERVER['HTTPS']) && $_SERVER['HTTPS'] !== 'off'),
    'httponly' => true,
    'samesite' => 'Lax',
]);
```

The `secure` value depends solely on `$_SERVER['HTTPS']`. It does **not** consider `X-Forwarded-Proto` or `SERVER_PORT`, unlike the rest of the application. `helpers/seo_helper.php` (lines 219-222 and 146-151) determines HTTPS from `$_SERVER['HTTPS']` **or** `SERVER_PORT === '443'` **or** `HTTP_X_FORWARDED_PROTO === 'https'`, and emits `Strict-Transport-Security` on that basis (lines 227-229).

The result is an internal inconsistency: on a request the application itself classifies as HTTPS (HSTS emitted), the session cookie is not marked `Secure`. This was confirmed against the running instance by sending `X-Forwarded-Proto: https` with a non-local `Host`: the response carried the HSTS header but the `Set-Cookie` line lacked `Secure`.

## Proof of Concept

1. Send a request that the application classifies as HTTPS via the forwarded-proto signal, using a non-local `Host` so the HSTS branch is taken.
2. Observe the response headers.
3. Note that `Strict-Transport-Security` is present (application believes the request is HTTPS) while the `Set-Cookie: PHPSESSID=...` line omits the `Secure` attribute.
4. Repeating without the header (or with `Host` local) produces the same cookie flags, confirming `secure` is never set when `$_SERVER['HTTPS']` is absent.

````bash
# Response is treated as HTTPS (HSTS emitted) yet the session cookie lacks Secure
curl -s -i -H "X-Forwarded-Proto: https" -H "Host: dimspersonal.my.id" \
  http://172.17.112.1:8001/login -D - -o /dev/null | grep -iE "set-cookie|strict-transport"
```

Observed:

```http
Set-Cookie: PHPSESSID=hh5q0hgt2qii0p2q2dd06juaqh; path=/; HttpOnly; SameSite=Lax
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
````

## Code Analysis

**Location 1:** `helpers/token_helper.php` (lines 13-17)
  Session cookie params: secure derived only from $_SERVER['HTTPS']
  ```
  session_set_cookie_params([
  ```

  **Suggested Fix:**
```diff

+                     'httponly' => true,
+                     'samesite' => 'Lax',
```

## Remediation

Determine the request scheme using the same logic already used elsewhere in the application (a single shared helper). Mark the session cookie `Secure` whenever the request is HTTPS by any of: `$_SERVER['HTTPS']` set, `SERVER_PORT` equal to `443`, or `X-Forwarded-Proto: https`. Only trust forwarded headers from known proxy addresses. As defence in depth, enable `session.cookie_secure` and consider HSTS `preload` plus an HTTP-to-HTTPS redirect so no cleartext request can carry the cookie.

## Assumptions

Assumes the production deployment terminates TLS at a reverse proxy that conveys the scheme via `X-Forwarded-Proto`/`SERVER_PORT` rather than setting `$_SERVER['HTTPS']`, which is consistent with the application's canonical URL (`https://dimspersonal.my.id`) and its own proxy-aware HTTPS detection elsewhere. On the provided lab target (plain HTTP) the same code path yields no `Secure` by design.
